# API Rate Limiter — Complete Guide

## 🎯 What This Project Does (Simple Explanation)

Think of a mailbox at a store. If someone could mail thousands of letters instantly, the mailbox would break and real mail wouldn't get through. This project is like a smart receptionist who says: "I'll accept 3 letters from you per hour, but after that, come back later." It protects your API from being attacked by spam or broken code.

**In tech terms**: A rate limiter that counts how many requests each IP address sends and blocks them (returns error 429) if they exceed the limit.

## 🏗️ What We Built

### Phase 0 (Foundation)
1. **Memory Store** (`src/lib/rate-limit/memory-store.ts`) — A fast counter that tracks requests. Cleans up old data automatically.
2. **Rate Limiter** (`src/lib/rate-limit/limiter.ts`) — The logic that decides "allow" or "block" using fixed-window algorithm.
3. **Middleware** (`middleware.ts`) — Sits between user and API, checks limits on every request.
4. **API Routes** — 3 test endpoints: `/api/ping`, `/api/echo`, `/api/contact`.

### Phase 1 (Observability) — COMPLETED
5. **Metrics Collector** (`src/lib/rate-limit/metrics.ts`) — Tracks stats: total requests, allowed, blocked, active IPs, requests/second.
6. **Metrics Endpoint** (`src/app/api/metrics/route.ts`) — Exposes live stats as JSON so dashboard can show real-time data.
7. **Updated Middleware** — Records every request (allowed or blocked) in metrics.

### Phase 2 (Dashboard UI) — JUST COMPLETED
8. **Live Dashboard** (`src/app/page.tsx`) — Visual dashboard showing:
   - Stat cards: Total Requests, Allowed, Blocked (429), Active IPs, Blocked %, Req/sec
   - Line chart: Requests/second over last ~1 minute
   - Bar chart: Blocked vs Allowed per endpoint
   - Tables: Per-endpoint breakdown, Recent Requests (last 50)
   - Testing instructions directly on page
   - Polls `/api/metrics` every 2 seconds, fail-open if endpoint down

## ⚙️ How It Works (Step-by-Step)

### The Flow
```
User → Browser/curl → Request to /api/ping
  ↓
Middleware intercepts
  ↓
Middleware asks: "Is this IP under the limit?"
  ↓
Memory Store answers: "Yes, 2 more allowed" or "No, blocked"
  ↓
Middleware records in Metrics: "Request allowed/blocked from IP X.X.X.X"
  ↓
Response sent back with headers (X-RateLimit-*)
  ↓
Dashboard polls /api/metrics → Shows "Total: 5, Allowed: 4, Blocked: 1"
```

### Edge Cases We Handle
- **Memory leaks**: Old IPs auto-remove after 5 minutes (TTL cleanup)
- **Per-IP tracking**: Different IPs get separate counters (1.2.3.4 ≠ 5.6.7.8)
- **Fail-open**: If limiter crashes, requests still go through (better than breaking)
- **Metrics cleanup**: Recent requests list keeps only 50 items (not 10,000)

```bash

```
**Look for** (scroll up in output):

```bash

done
```
**Expected**:
- Requests 1-10: Status `200 OK`

1. Open terminal
2. Navigate to project: `cd /path/to/API-limiter`


   ```bash
   curl http://localhost:3000/api/metrics | grep -E '"total"|"allowed"|"blocked"'
   ```
   Should show: `"total":5,"allowed":5,"blocked":0`

5. **Hammer the endpoint** (make 10 more):
   ```bash
   for i in {1..10}; do curl -s http://localhost:3000/api/ping > /dev/null; done
   ```

6. **Check metrics again**:
   ```bash
   curl http://localhost:3000/api/metrics | grep -E '"total"|"allowed"|"blocked"'
   ```
   Should show: `"total":15,"allowed":10,"blocked":5`
   (because ping limit is 10/min, so 5 were blocked)

7. **Verify blocked message**:
   ```bash
   curl http://localhost:3000/api/ping
   ```
   Should show: `"code":"RATE_LIMITED","message":"Rate limit exceeded. Try again in ~59s."`

## 📊 Understanding the Output

### X-RateLimit Headers
```
X-RateLimit-Limit: 10         ← Maximum allowed per minute
X-RateLimit-Remaining: 3      ← How many left in this window
X-RateLimit-Reset: 1725081200 ← Unix timestamp when window resets
Retry-After: 59               ← Seconds to wait (only on 429)
```

### Metrics JSON Fields
```
total: 15              ← All requests made (200 + 429)
allowed: 10            ← Requests that succeeded (200)
blocked: 5             ← Requests that got 429
activeIPs: 1           ← Unique IP addresses seen recently
requestsPerSecond: 2.1 ← Average over last 60 seconds
endpoints: {           ← Stats per endpoint
  "ping": {total: 15, allowed: 10, blocked: 5}
}
recentRequests: []     ← Last 50 requests for dashboard
```

## 🔧 Configuration (Change Limits)

Edit `src/lib/rate-limit/config.ts`:
```typescript
export const endpointConfig: Record<string, RateLimitConfig> = {
  ping: { windowMs: 60_000, limit: 10 },      ← 10 per minute
  echo: { windowMs: 60_000, limit: 5 },       ← 5 per minute
  contact: { windowMs: 600_000, limit: 3 },   ← 3 per 10 minutes
};
```

**After changing**: Save file, server auto-reloads in dev mode.

## 🚨 Troubleshooting

| Problem | Solution |
|---------|----------|
| `Connection refused` | Server not running. Run `npm run dev` |
| Port 3000 in use | Run on different port: `PORT=3001 npm run dev` |
| Headers not showing | Use `curl -i` (lowercase i) instead of `-I` |
| Metrics always 0 | Middleware might not be loaded. Restart server: `Ctrl+C`, then `npm run dev` |
| Per-IP not working | Add `-H "x-forwarded-for: X.X.X.X"` header to curl |

Great vision — you're thinking like someone who's built real systems. Let me give you my honest take on what's worth doing and what's overkill.

What I Agree With (High Value)

1. The live simulator is the killer feature. You're 100% right. "Click this button and watch requests turn from 200 → 429" is infinitely more impressive than "I implemented a rate limiter." This is the single thing that transforms a learning exercise into a demo-able portfolio piece.

2. Metrics + dashboard. Real systems are judged by observability. Tracking totalRequests, allowedRequests, blockedRequests, activeClients, and per-endpoint stats turns your black-box limiter into something you can actually operate. This is essential, not optional.

3. Redis upgrade with multi-instance demo. The "3 instances each showing counter=7" visualization is brilliant. It makes the abstract concept of "distributed rate limiting" concrete. This is a strong differentiator.

4. Configurable limits. Making limits explicit and adjustable (not hardcoded) is good practice and makes the dashboard meaningful.

What I'd Skip or Simplify

1. Multiple algorithms (fixed-window, sliding-window, token-bucket).
- Skip for now. Implementing 3 algorithms correctly is a lot of code, and for a portfolio demo, one well-explained algorithm is stronger than three shallow ones.
- Better approach: Pick fixed-window (you already have it), explain it clearly in docs, and note the others as future work. If you do add another, sliding-window is the most impactful (fixes the boundary problem).

2. API keys / client tiers.
- Skip for now. This adds authentication, key storage, and a whole separate concern. It distracts from the core rate-limiting concept.
- Better approach: Mention it as a roadmap item. The IP-based approach is sufficient to demonstrate the concept.

3. Docker / Docker Compose.
- Skip for now. For a learning/demo project, npm run dev is enough. Docker adds deployment complexity without adding demonstration value.
- Better approach: If you want to show multi-instance, use a simple approach — run the same dev server on different ports manually, or use a Node.js cluster. The Redis demo can be done with Upstash (free tier) without Docker.

4. k6 / autocannon load testing.
- Skip the external tools. The live simulator in the UI already does this job better and is more interactive.
- Better approach: Use your own simulator page. It's more portfolio-worthy than integrating a third-party load tester.

5. The full limiter/ directory with 3 algorithm files.
- Skip. You already have a clean structure. Don't over-engineer the directory layout before you know what you're building.
